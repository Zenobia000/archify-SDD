ADR-0001：簽核內建於請假服務

长图

答

结论

LeaveFlow 把簽核做成請假服務內的一個模組，不另建共用簽核引擎，也不採用 BPM 產品。

  1. 目前只有請假需要簽核，請假專用的關卡規則用程式寫最快交付。
  2. 簽核動作、額度實扣與 outbox 事件可以在同一個資料庫交易內完成。
  3. 少一個服務或一套 BPM 平台要部署、升級與監控。

适用于LeaveFlow（虛構）· 請假簽核狀態：已採納

1

這個決策要解決什麼問題？

請假簽核的關卡會隨假別與天數改變。不超過 3 天由直屬主管簽，超過 3 天加部門主管。婚假、喪假、公假與超過 3 天的病假，還要附證明並加人資審核關。

簽核人可以退回補件、臨時加簽，會簽關卡要全部同意才通過。關卡 24 小時未簽會提醒，48 小時自動升級給上一層主管。

核准時要實扣額度，並通知出勤、薪資與行事曆。這些變更必須一致：不能出現假單已核准、額度卻沒扣的情況。

範圍

目前只有請假走簽核。加班、出差、報銷尚未納入 LeaveFlow。

2

考慮過哪些選項？

比較項目A 請假服務內建簽核模組B 共用簽核引擎服務C 採用 BPM 產品（如 Camunda、Flowable）
交付速度快最快，沿用請假服務的程式與資料庫較慢要先設計通用 API 與表單模型最慢要導入平台、建模與整合
規則彈性需發版規則寫在程式，改規則要發版規則抽象成設定，通用但較繞最高流程圖可視化設定
維運成本低不增加部署單元中多一個服務與資料庫高多一套平台與引擎資料庫
跨表單重用不可重用只服務請假可重用加班、出差、報銷可共用可重用
交易一致性單一交易簽核與額度同一交易跨服務，需要補償或事件跨系統，需要補償或事件
3

決定採用哪個選項？

图的结构
  • 員工入口 portal
  • 簽核服務 approval
  • 路由引擎 routing
  • 額度服務 balance
  • 請假資料庫 leave-db
  • portal → approval
  • approval → routing
  • approval → balance
  • approval → leave-db

採用 A：請假服務內建簽核模組。簽核服務、路由引擎與代理解析是請假服務內的元件，與假單、額度共用同一個請假資料庫。

  1. 簽核服務 ↗

    收到主管的核准或駁回，檢查代理權限後記錄動作；會簽全部同意才往下走。

  2. 路由引擎 ↗

    依假別與天數決定下一關；沒有下一關就結案。

  3. 額度服務 ↗

    最後一關通過時，把預扣轉成實扣。

  4. 請假資料庫 ↗

    動作、額度、假單核准與 outbox 列一起提交；事件發佈器之後送出 leave.approved。

4

這個決策帶來什麼影響？

影響性質
第一版只需交付請假服務，不必先做通用簽核平台正面
簽核、額度與 outbox 在單一交易內，不需要補償流程正面
部署單元與維運監控維持現狀正面
路由規則寫在程式中，調整天數門檻或假別要發版負面
其他表單無法直接重用簽核；日後抽離需要搬移資料表與 API負面
業務人員無法自行設定流程，需要開發團隊協助負面
5

什麼情況要重新評估？

  • 加班、出差或報銷也需要簽核時，把 approval 模組抽離成共用簽核服務。
  • 路由規則需要業務人員自行設定，且改版頻率高過發版節奏時，評估 BPM 產品。
  • 會簽、加簽之外出現平行分支或子流程等需求時，重新比較選項 B 與 C。

降低日後抽離成本

簽核資料表集中在 approval_steps、approval_actions、delegations，抽離時搬移範圍明確。
